## P1. Stop-hook per-instance (session-end-reminder) — идея Богдана, ПОДТВЕРЖДЕНА разведкой

**Проблема (факт):** `hooks/session-end-reminder` детектит изменения голым `git status --porcelain` (строки 225-227, 283) без какого-либо учёта инстанса. Реестр claims в `coord.sh` (claims.json, `{relpath: {by, at}}`) существует, но хуком не используется. Дизайн coord рассчитан на «инстанс = свой worktree», а фактически Богдан гоняет 2-3 инстанса в ОДНОМ worktree — отсюда напоминания за чужие файлы.

**Решение:** вести per-session реестр реально изменённых файлов. Механика: `post-edit-check` (PostToolUse, уже получает путь файла) дописывает путь в `$XDG_CACHE_HOME/claude-subteams/session-edits/<session_id>`; `session-end-reminder` при `CLAUDE_SUBTEAMS_MULTI_INSTANCE=1` пересекает `git status` с этим списком (+ файлы, заклеймленные этим инстансом). Bash-правки (git mv, sed) реестр не поймает — честно деградируем: если пересечение пусто, но есть чужие изменения, молчим (сейчас — шумим, что хуже).

**Объём:** ~40 строк bash в двух хуках + тест. Риск низкий, хук advisory-only.

## P2. Автономный луп-режим (loop engineering) — СТРОИТЬ НА СУЩЕСТВУЮЩЕМ

**Что уже есть (факт):** autonomy mode = run record в IMPL-PLAN (грант, scope-globs, капы файлов/строк, чекпоинты через `autonomy-check.sh`, enforcement через PreToolUse `autonomy-gate`); living-plan = эволюция плана по ходу (immutable acceptance criteria + REVISED-строки с ack оператора, статус-токены по пунктам, `check-plan.sh`). То есть «проходить по каждому пункту плана и дописывать план» уже спроектировано на 70%. НЕ хватает самого ЦИКЛА: сейчас один грант = один интерактивный отрезок, нет внешнего цикла «пункт → пайплайн → чекер → следующий пункт», нет автоматического re-prompt.

**Предложение — новый скилл `autonomous-loop` + скрипт `scripts/loop-runner.sh`:**
1. Вход: IMPL-PLAN с run record + грант Богдана «работай по плану автономно».
2. Цикл (в одной сессии, без headless): взять первый пункт со статусом `[ ]` → выполнить по пайплайну (developer → review → fix) → механический чекер (`tsc && vitest run && check-plan.sh && autonomy-check.sh --checkpoint`) → зелено: пометить `[x]`, следующий пункт; красно: одна попытка починки, потом blocker-checkpoint.
3. Перезапись плана: разрешена в рамках living-plan (добавить/разбить пункты — можно; менять acceptance criteria — только REVISED с эскалацией Богдану).
4. Стоп-условия: план закрыт / blocker / кап токенов / kill-switch (любое сообщение Богдана).
5. Отчёт: сводка по пунктам + evidence чекпоинтов.

**Почему не headless-цикл (`claude -p` в while, «ralph»):** на VPS 3.8 ГБ и при Max-подписке лишние полные сессии дороги; внутрисессионный цикл + Stop-hook-«подталкиватель» (см. P3.3) даёт то же с меньшим расходом. Headless-вариант можно добавить позже вторым режимом.

**Объём:** скилл (~150 строк) + loop-runner чекер (~60 строк bash) + правка executing-plans (§Autonomy Mode ссылка). Средний риск: главное — не ослабить существующие капы.

## P3. Enforcement-хуки (лечение «театра» без резки скиллов)

Аудит: модель удерживает лозунги, но не 24 правила. Скиллы НЕ режем (решение Богдана), вместо этого переносим критичные правила из прозы в механику:

1. **`pre-commit-gate` расширить** (сейчас Bash-матчер уже есть): блокировать `git commit`, если в сессии был логик-дифф по src, а code-reviewer не запускался (маркер-файл от Agent-вызова ревьюера в cache, как session-edits в P1). Это главное правило пайплайна, станет механическим.
2. **Convention pre-flight** (идея Богдана про «проверку перед правкой»): PreToolUse-хук на Edit/Write — быстрые статические проверки ДО записи: файл в grandfathered-списке и правка его наращивает? импорт «вверх» по слоям CONVENTIONS? файл превысит лимит? → deny с объяснением (в обычном режиме — warn, в autonomy — deny). Семантическую проверку «не сломает ли логику» хук дать НЕ может — это остаётся за code-reviewer + тестами; обещать её в хуке = ложная уверенность.
3. **Stop-hook «loop nudge»:** когда активен autonomy-run и план не закрыт, Stop-хук возвращает additionalContext «план не закрыт, следующий пункт N» — механическое продолжение цикла P2 без участия Богдана.
4. **Лозунги в вершину скилла** (вопрос Богдана «лозунги добавить надо?» — да): первые 10 строк using-subteams = 5 несущих лозунгов (классифицируй масштаб; любая логика → ревью; заявление → evidence; не подменяй согласованное; при неуверенности — спроси). Остальной текст — справочник по ссылкам. Это не добавка текста, а перестановка приоритета.

## P8. Гигиена Stop-хуков — проблема, поднятая Богданом 13.07

**Две наблюдаемые проблемы** (воспроизводились в реальных сессиях):
1. «Съеденный ответ»: модель написала финальный ответ человеку → Stop-хук вернул additionalContext → модель ответила уже на хук, и человек видит ответ на хук вместо задуманного ответа.
2. «Спровоцированная работа»: контекст хука может подтолкнуть модель продолжить работу, хотя она ждала подтверждения человека.

**Правила (для всех Stop-хуков плагина, включая будущий loop-nudge):**
1. **Advisory → только systemMessage.** Напоминания для ЧЕЛОВЕКА (доки не обновлены и т.п.) доставляются как systemMessage (виден человеку) БЕЗ additionalContext (не виден модели). Человек сам решает, просить ли обновление. Это убивает обе проблемы для advisory-класса.
2. **Перенос doc-reminder с Stop на pre-commit-gate.** Естественный момент «проверь доки» — коммит, а не конец каждого хода. Stop-поверхность сокращается почти до нуля.
3. **Если additionalContext необходим** (управляющий класс, не advisory) — обязательная шапка: «Это не сообщение пользователя. Если ты ждал подтверждения — продолжай ждать и повтори свой вопрос дословно. Если твой финальный ответ уже написан — повтори его дословно первым блоком, потом реагируй».
4. **Loop-nudge (P3.3) — строго за грантом:** additionalContext отдаётся ТОЛЬКО при живом autonomy-run record (явный грант Богдана в текущем контракте, см. P2) — тогда «продолжение работы» и есть санкционированное поведение. Нет гранта → хук молчит всегда. Плюс существующий kill-switch: любое сообщение Богдана = немедленная остановка цикла.
5. **Cooldown обязателен** для любого повторного срабатывания (образец уже есть: 45 мин в session-end-reminder).

## P9. Смысловая целостность вместо жёсткого лимита строк — решение Богдана 13.07

Жёсткое «никогда файлы >200 строк» из дефолтов плагина (using-subteams Critical Rule 14, clean-architecture, post-edit-check warn на 200) признано неверным: файл, описывающий один класс/процесс на 1000+ строк, резать на хелперы ради счётчика — вредно, теряется смысловая целостность.

**Новая формулировка (внести в 1.32 в clean-architecture, using-subteams Rule 14, post-edit-check):**
- Первичный принцип — **cohesion**: файл/класс/функция = одна смысловая единица. Резать по смыслу, никогда — по счётчику.
- Размер — не нарушение, а **сигнал ревью**: порог (по дефолту 300 строк, проект переопределяет в CONVENTIONS.md) означает «остановись и проверь: это всё ещё одна ответственность?» Если да — файл живёт любого размера с одной строкой обоснования; если нет — резать по смысловым швам.
- Анти-злоупотребление: «смысловая целостность» не оправдывает god-файл из несвязанных вещей; признак подмены — файл, который меняется по несвязанным причинам (нарушение SRP по оси изменений, а не по строкам).
- post-edit-check при наличии проектного CONVENTIONS.md берёт пороги оттуда, а не хардкод 200.
